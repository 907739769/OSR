# 热门自动订阅

TMDb 榜单与 RSSHub 豆瓣源，标题补全的判据与地址拼接。

> 本文件由根 `AGENTS.md` 拆出，只在改到本目录时才载入。全局约定（分层、命名、异步包装、日志纲领）仍在根 `AGENTS.md`。
> 新增本域的踩坑记录写这里，不要往根 `AGENTS.md` 里塞。

## NOTES
- **热门自动订阅的豆瓣源（`RSSHUB_DOUBAN`）拉回来的条目<b>没有 tmdbId</b>，补全那一步是整个功能唯一会造成实际损失的地方**。TMDb 的热门榜以欧美内容为主，华语与日韩内容的「热」在豆瓣上才反映得出来；但 RSSHub 的豆瓣路由只给标题和条目链接，不给 IMDb ID 也不给 TMDb ID，而整条建订阅链路（订阅表、集号对齐、索引器的外部 ID 检索）都是围绕 tmdbId 建的。`PopularItemResolver` 按标题搜 TMDb 补全，五条不要改坏的：
  1. **判据是「归一化标题<b>全等</b>」，不是包含也不是相似度**（复用 `TitleNormalizer#normalizeForCompare`，与 TMDb 刮削侧「全等命中自成一档」同一条取向）。误匹配的后果不是"没订上"，而是**订错剧并真的开始占用索引器与下载器去下一部用户没要的作品**，而日志里每一步看着都正常、没有任何一层能发现。漏掉的会以 `SKIPPED_NO_MATCH` 落进执行日志，用户看得见、能手动补订——两种失败的代价差着数量级，所以宁可漏不可错。放宽到包含的话《三体》立刻会匹配上《三体动画版》。**但「全等」比的对象必须<b>包含中文别名</b>，不能只比 name/original_name**：TMDb 缺 zh-CN 翻译时 name 会直接退回英文（与 NFO 里作品标题那条坑同源），而豆瓣给的恰恰只有中文名——《足球教练》(Ted Lasso) 的 name 与 original_name 都是 `Ted Lasso`，逐字比对必然落空、被记成「TMDb 未搜到标题一致的剧集」，而 TMDb 上「足球教练」这个名字是有的、搜索也确实返回了这个条目。做法是**两轮**：第一轮比条目名，零额外请求（TMDb 有中文 name 是常态，那种情况一次别名请求都不多打，同查询词分段与裸数字回退的早停取向）；全落空后才对**前 3 个**候选各查一次 `/alternative_titles`。三条边界：**判据仍是全等，一点没放宽**（alternative_titles 是众包数据，噪音比条目名大得多，在这里放宽等于给误匹配开一扇更大的门），只查前 3 个也是同一个理由——正确答案排在 3 名之外还得靠众包别名才认得出的情形，收益抵不上给长尾同名作品增加的撞上机会；**要比<b>全部</b>中文别名而不是优先级最高的那一个**（`TmdbSearchService#listChineseAliases`，挑显示名的 `resolveChineseTitle` 现在取它的第一个，两者共用一份判据），同一部作品在 CN/TW/HK 常登记着不同译名（CN 是「泰德·拉索」、别处才是「足球教练」），只比 CN 那个等于没修；**地区仍限 CN/TW/HK/SG**（`TmdbTitleRegions.CHINESE`），日文汉字落在同一个 Unicode 区段内，只按「含中文」筛会把 JP 条目当成中文名。年份检验在第一轮就把候选挡掉了，别名轮拿到的候选年份本就可接受——同名重拍版不会因为多了这一轮而被放进来。
  2. **年份不传给 TMDb，只在本地校验，容差 1 年**。传过去是精确过滤，两边差 1 时结果直接为空，而跨年播出的剧两边各记一年是常态；容差放到 2 就开始吃进相邻年份的同名重拍版。**来源没有年份时不检验**（豆瓣路由多数不给年份，要求必须有等于把这个源废掉），但**来源有年份而候选没有则拒绝**——能拿到一半信息却对不上，比两边都没有更可疑。
  3. **补全必须排在过滤<b>之前</b>**。规则上的「排除类型/最低评分/最低评分人数」三个字段全部来自 TMDb，不补的话它们对豆瓣源恒为 null，按"不达标"处理会一条都放不过。顺带这也让两个源的过滤口径完全一致——**豆瓣自己的评分刻意不用**，它是另一套口径，混进来会让「最低评分 7」这个数字在两个源里含义不同。字段映射收口在 `TmdbItemMapper`（榜单与搜索返回的条目结构本就一致），各写一份的漂移表现是"同一部作品在两个源里算出不同的评分人数"。
  4. **标题清洗只剥<b>带小数点</b>的尾部评分**（`DoubanRssParser`）。豆瓣评分一律一位小数，而放开成「尾部孤立数字」会把《速度与激情 9》的序号当成评分剥掉——那类片名在榜单里相当常见，剥错之后标题全等判定必然落空，且完全静默，只表现为"这部片一直订不上"。尾部年份括号剥掉并带出年份，但**剥空则不剥**（《1917》这类以年份为名的作品）。
  5. **查询词分段有早停**：整串优先，整串搜不到时才依次拿中文段/拉丁段、剥掉尾部裸数字的标题各试一次（豆瓣条目存在「中文名 English Name」拼接的写法，整串搜 TMDb 必然一条都对不上）。纯中文或纯英文标题不分段。常见情况下每个候选只打一次 TMDb。
  6. **「片名 + 裸数字」（`问心2`、`庆余年2`）只能做成排在最后的<b>回退查询</b>，不能像「第九季」那样直接剥**。尾部裸数字究竟是季号还是<b>片名的一部分</b>，正则判不出来——「问心2」是《问心》第 2 季，而「速度与激情9」的 9 是片名自带的（TMDb 上的条目名就长这样），两者形态完全一致。做成回退之后这个歧义就不需要判：完整标题先搜、《速度与激情9》直接命中根本走不到这一步，只有完整标题落空时才试剥数字，而那正是「问心2」的处境；剥完仍要过标题全等判定。**因此它绝不能放进 `SeasonSuffix`**——那个类被刮削链路共用，而刮削侧是拿解析出的标题直接查 TMDb、没有「先试完整再试剥掉」这一层兜底，把裸数字规则放进去会让《速度与激情9》在刮削侧被剥成《速度与激情》，那是另一部电影。**电影整个不启用**：电影续集在 TMDb 上的条目名通常就带数字，而剥数字对电影的失败方向是<b>订到前作</b>（下错片子），剧集没有这个问题——季本就是作品下面的一层。三条边界：剥完仍以数字结尾则放弃（`1917` 会被切成 `19`+`17`）、剥完长度不足 2 则放弃、季号取值限 2~99（1 不产生新查询词，第 1 季本就是默认）。命中后那个数字即季号，但**来源已解析出季号时不覆盖**（`第九季` 比回退猜的确定）。
  **榜单里电影剧集常混在一起，而 RSSHub 给的信息不足以判断条目属于哪一类**——一律按规则选定的 `media_type` 处理，类型不符的条目会在 TMDb 搜索那步匹配不上而被跳过。不要试图从条目里猜类型。
- **RSSHub 的地址分两层：全局 `openlist.rsshub.base-url` 管「实例在哪」，规则上的 `source_url` 管「拉哪个榜单」**。官方 RSSHub 实例常年限流/不可用，这个功能实际可用的前提就是用户自建实例，所以地址必须可自定义。四条：**`source_url` 填成完整 http(s) URL 时直接使用、忽略 base**（于是这个源顺带支持任意 RSS 地址，不限于豆瓣）；**拼接走 `HttpUrl` 而不是字符串拼接**——base 带访问码（`?key=xxx`）时 query 要保留，路径要接在 base 已有 path 之后（反代到子路径是常见部署方式）；**base 未配置时直接跳过并 warn，不去猜一个官方地址**（猜出来的地址会把"没配置"这个明确故障变成"看起来配好了但一条都拉不到"）；**日志打地址时去掉 query 保留 path**，访问码通常就挂在 query 上，而 path 本身已足够认出是哪个榜单——与 TMDb 回源日志只打 `encodedPath` 是同一条理由。前端的榜单预设**只是省打字、不是白名单**，地址框照常可以手填：RSSHub 的路由路径在版本之间变过，写死会随对方升级而失效。
- **用户删掉的自动订阅不能再被自动加回来，判据是「这一季存在过 ADDED 日志」**（`IPtAutoAddLogPlusService#everAdded`，结果记 `SKIPPED_REMOVED`）。订阅表里没有而 ADDED 日志里有，只可能是用户手动删了；不拦的话只要它还挂在榜上，下一轮就原样回来并重新开始下载。由此两条连带约束：**ADDED 日志永久保留**，`purgeSkippedBefore` 只清 30 天前的非 ADDED 行（清掉的话保留期一满，被删的订阅就自动回来）；判据跨规则，**任一规则**订过都算。
- **跳过类结果（已存在/已删除/过滤）同一条目只记第一次**（`alreadyLogged`），否则榜单 20 条一天一轮，几天后「最近 100 条」全是逐字相同的「已存在」，ADDED 被挤出去。`SKIPPED_NO_MATCH` **刻意不去重**：豆瓣条目隔 `NO_MATCH_RETRY_DAYS`（7 天）才重搜一次 TMDb，靠的正是「最近一条日志的时间」，去重会让那条时间永远停在第一次，过期后变成每轮都重搜。上一轮已匹配到 tmdbId 且该季已订/已删的豆瓣条目也走捷径不重搜（`settledBefore`）；**被过滤掉的不走捷径**——评分等字段来自 TMDb、会变。
- **拉榜失败不推进 `last_run_time`**，下一个 30 分钟心跳就重试（推进的话要白等一整个 `interval_hours`）；重复失败用 `FaultThrottle` 压住，报告的那一次同时写一条 `FETCH_FAILED` 执行日志——页面只看得到这张表，只写应用日志的话用户看到的是「一直没加」。手动执行时 `AutoAddRunResult.fetchError` 单独带回失败原因，否则拉榜失败与「榜上没有新东西」都是 0/0/0。
- **`last_run_time` 只 set 这一列，不许 `updateById(rule)`**：豆瓣源一轮可能跑几十秒，整条写回会把执行期间用户在页面上改的规则静默覆盖。**同一条规则同一时刻只跑一份**（`runningRules`）：「立即执行」与定时任务撞上时两边会对同一批条目各建一次订阅，后到的撞唯一约束被记成 FAILED——明明订上了日志却说失败。前端「立即执行」超时放宽到 3 分钟，理由相同（默认 15 秒必然超时，页面报错而后端还在建，用户会再点一次）。
