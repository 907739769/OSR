# PT 资源搜索

不建订阅、按关键词直接搜全部站点的那一页（`ResourceSearchService` + `PtResourceSearchRestController`，前端 `views/openlist/ptSearch` 两端）。

> 本文件由根 `AGENTS.md` 拆出，只在改到本目录时才载入。全局约定（分层、命名、异步包装、日志纲领）仍在根 `AGENTS.md`。
> 新增本域的踩坑记录写这里。

## NOTES
- **检索、去重、解析、H&R 标记与订阅内手动搜索共用同一份实现，不要在这里另写一份**（`SearchSupplementService#searchKeyword` / `#toCandidateDtos` / `#torrentOf`，`SubscriptionEngine#markHitAndRun` / `#fillParsed` / `#savePathFor`）。两边各写一份的表现是「资源搜索页看到 2160p、订阅里同一个种子是 1080p」或「这里推下去落进 /电影、订阅推下去落进 /剧集」——不报错，只是同一个种子在两个入口得到不同答案。站点范围的语义也照搬（`resolveIndexerScope`）：**勾选的站点全部不可用时报错，绝不退回搜全部**，勾选站点多半是为了避开某个站。
- **全局过滤规则只标注、不淘汰**（`SearchCandidateDTO#ruleRejection` 短标签 + `#ruleRejectionDetail` 带实际值与阈值）。用户来这一页正是要看「站上到底有什么」，按规则滤掉一批的话他会以为站上没有；而「这条会因为分辨率不在白名单被挡」恰好回答了「为什么我订了却没自动下」。三条：用的是**全局**规则、不带任何订阅级覆盖（没有订阅可取）；**原始语言传 null**，「中字」那一项按影片原语言判、这里判不了，宁可不标也不能乱标；**判定本身出错时照样返回结果、只是不带标注**，不能让一张坏掉的规则配置把搜索整个拖垮。体积规则按每集判定时要先折算集数（`EpisodeCountResolver.resolve(t, null, looksLikeMovie)`），否则季包会被成片标成「体积超上限」。
- **直接下载不建下载记录，这是权衡后的结论，不是漏做**。`pt_download_record.sub_id` 是 NOT NULL，下载追踪、记录页的归属隔离（`DownloadRecordAdminService#canAccess`）、统计、完成后提前对账（`DownloadCompletionSyncService` 直接 `refresh(record.getSubId())`）都以「记录属于某个订阅」为前提，为这一个入口放开要逐处审三十来个调用点。于是直接下载的种子在 OSR 看来与用户在下载器里手动加的种子是一回事：不追踪进度、**不下发 H&R 分享限制**（那一步在 `DownloadTrackService` 里、依赖记录）、不进下载记录页；下载完成后按目录触发的同步 / STRM 照常生效。四条不要改坏的：
  1. **标签用 `osr-manual`，绝不能带下载器的跟踪标签**（`downloader.getTag()`）。后者会让 `DownloadTrackTask` 按标签拉回一个没有记录与之对应的种子。
  2. **只做种（SEED_ONLY）与停用的下载器一律拒绝**，判据与订阅推送同一份（`participatesInDownload()`）——保种机开着按「保种」设计的清理规则，新下载推上去会被当保种种子清掉。下拉框（`/downloaders`）也只列这一类，两处口径一致。
  3. **限管理员**：它绕开了订阅、种子没有归属，多用户部署里不该让每个人都能往下载器里塞东西；普通用户走「转为订阅」。搜索本身对登录用户开放（与订阅内手动搜索同一档）。前端按 `roles.includes('admin')` 藏按钮只是减少误点，挡人的是后端 `denyIfNotAdmin`。
  4. **H&R 站点的候选，推送弹窗要明说不会照看考核**（`ResourcePushDialog`）。不说的话用户会默认它和订阅下的一样被追踪。
  真要让直接下载也被追踪，正确的做法是先给订阅之外的下载建一个归属概念，而不是把 `sub_id` 改成可空了事。
- **作品识别（`identifyWorks`）有四条不能改坏的判据**，它们各自对应一次真实的全绿事故——测试当时是绿的，因为 `TMDbClient` 被 mock 掉了：
  1. **`TMDbClient#matchTmdbId` 返回的是 id，不是标题。** `search()` 交出来的是 `getBestTitle` 的标题，id 只写在 `info.setTmdbId` 上；直接 `return search(...)` 会把「斗破苍穹」当成 id 交出去，调用方 `Integer.parseInt` 必炸。**守它的用例必须走真实 `TMDbClient`**（`TMDbClientMatchTmdbIdTest`，用 `mockStatic(SpringUtils)` 喂假 `TMDbApiService`），mock 掉 client 的用例拦不住。它还**只判定身份、采纳后什么都不再拉**（`search(..., identityOnly=true)`）：`enrich` 那条路采纳候选后要取规范标题、详情，并发拉图片 / 外部 ID / 分级 / 季图片，那是给刮削写 NFO 用的，一个作品 5~6 个请求；识别只要一个 id，展示用的名字与年份由 `TmdbSearchService#describeWork` 另取（一次详情请求）。把那几个请求加回来不会让任何功能出错，只会让每次搜索多发上百个请求、全部挤在并发 4 的信号量上吃掉识别预算——所以同一个测试类里有一条 `verify(api, never())` 守着。
  2. **类型一律在 `matchTmdbId` 入口归一小写。** `TMDbClient` 内部按小写全等判断（决定读 `title` 还是 `name`），且 type 直接拼进 `/search/` 路径；传大写时电影被当剧集取字段、集数反证整条失效。DTO 侧存的是大写 `TV`/`MOVIE`（与 `TmdbLink` 的大小写约定同一套），所以归一只能做在入口，不能指望调用方记住。
  3. **详情页取 RSS 的 `<comments>` 元素**，不是 `torznab:attr name="comments"`——按 Torznab 规范那个属性是**评论数**。`<link>` 已被当下载地址用掉时无法判断它是详情页还是直链，宁可不给：留一个点不动就跳到下载地址的链接，比没有这个链接更糟。**只收 http/https**（`TorznabParser`）：这个值原样成为页面上的 href，索引器给什么协议不由我们控制。
  4. **归并键是「归一化标题 + 类型」，电影再加年份，剧集不加**（`workKey`）。类型必须进键：只按标题归并会把同名电影的身份套给剧集。年份只对电影进键——电影的年份是上映年，同名不同年就是翻拍；**剧集种子上的年份是本季播出年**（见 `tmdb/AGENTS.md`），进键会把同一部剧按季劈开，一部八季的剧占掉八组，更容易撞上限让整页都不识别；有年份与没年份的种子也会被劈成两组。同名不同年的剧集因此归成一组，是有意的取舍。索引器自带的 `tmdbid` **只在 `ExternalIds.kindOf(categories)` 判得出大类时**才采纳——TMDb 的 `movie/1399` 与 `tv/1399` 是两部不相干的作品；判不出就退回标题匹配。已订阅标记同样必须带 `media_type`。
- **规则标注与作品身份都按下标把 `torrents` 的结论回填到 `items` 上**，前提是 `SearchSupplementService#toCandidateDtos` 一对一、不过滤、不重排。`search()` 在转换后立刻校验两边长度，不等就抛 `IllegalStateException`：静默继续的话结论会套到别的行上，而串了行的身份带着 TMDb 链接和「已订阅」标记，没有任何迹象可查。给 `toCandidateDtos` 加过滤或排序之前先来改这里。
- **标题组数超过上限（`pt.search.tmdb-lookup-max`，默认 20）时，只识别种子最多的那些组，不是整页放弃**。早先是超限就整页不识别，理由是「那时用户要的是站上有什么而不是哪部剧」——实测正相反：「Shingeki no Kyojin」100 条结果有 33 组标题（各季、剧场版、OAD、各字幕组各写各的），长寿动画恰恰是最需要识别的那类搜索，却一条都认不出。按组内种子数取是因为大组覆盖的行最多，剩下的多是只有一两条的零散写法。没问的那些组仍走 `tmdbLookupSkipped` 显式说明，且那时逐行不显示「识别不出」。
- **识别没跑、没跑完、被上限挡掉、TMDb key 未配置，四种状态都必须显式说出来**（`Result` 的 `tmdbLookupSkipped` / `tmdbLookupTruncated` / `tmdbLookupUnavailable` + 前端 `lookupNote`）。少了它，用户看到的是一片空白，而空白会被读成「这些种子不是任何作品」——真相是没识别。逐行的「识别不出」只在识别**完整跑过**时才显示（`lookupComplete`）。前端文案不写死上限数字（那个 20 在后端，写在这儿早晚漂移）。**计数有两个口径，不许摆成「X / Y」**：`distinctWorks` / `identifiedWorks` 是**标题组数**（同一部作品的中文名与英文名是两组），前端的 `matchedWorks` 是按「类型 + tmdbId」去重的**作品数**（一部剧 12 集是 12 行、1 个作品）。拿作品数除以组数会得到「识别出 1 / 3 个作品」这种读不通的话；「没跑完」那句用的是同口径的两个组数。
- **识别是并发的，这一层不自己压并发**（`identifyWorks`：虚拟线程 + `Threads.wrapSupplier`）。限流在更底层：`TMDbApiService` 有全局 `Semaphore(4)`、429 按 `Retry-After` 退避、L1 + DB 两层缓存，上层开多少线程都被封顶在 4。早先做成串行、理由是「怕并发太大」，那是没查依据的保守决定——等于把并发度从 4 压到 1，20 组标题很容易撞预算。两条别改坏的：**预算（`pt.search.tmdb-lookup-budget-ms`，默认 30 秒）是墙钟上的等待上限**，到点不再等、已识别的照常返回并标记「没跑完」，没跑完的任务不取消（结果进 TMDb 缓存，再搜一次直接命中）；**执行器不能用 try-with-resources**——`close()` 会等全部任务结束，预算就成了摆设。前端 `searchResourceApi` 的超时要盖住「索引器预算 + 识别预算」。**预算盖不住最坏情况，是有意的**：最坏请求量 = 组数上限 20 ×（标题 1 次 + 别名 3 次）× 每次识别的请求数（搜索 1~2 次，候选全是中日韩名时再加最多 5 次英文规范名探测），20 组全是冷缓存的罗马音标题时跑不完。实测远到不了那里（13 组冷缓存约 20 秒、5 组含别名兜底约 6 秒，均含索引器检索），跑不完的代价也只是这一次标「没跑完」、再搜一次就全了；为它把每次搜索的等待上限翻倍不划算。三个配置键（`tmdb-lookup` / `-max` / `-budget-ms`）在 `application.yml` 的 `pt.search` 段。
- **标题识别落空时拿 description 别名兜底，而且采纳比标题那条路更严**（`identifyByAlias`）。实测「Sousou no Frieren」100 条结果里 83 条识别不出：罗马音 / 拼音命名的种子，标题对不上 TMDb 的中文名、原名、英文名里的任何一个，而能对上的名字就写在 description 的别名列表里（`葬送的芙莉莲 / 葬送のフリーレン`）——页面副标题上明明显示着，下面却写「识别不出」。取别名与订阅匹配同一份（`DescriptionAliases#parse`）。四条不要改坏的：
  1. **搜到的作品必须与别名归一化后全等（中文名或原名）才采纳。** `matchTmdbId` 的门槛是「标题命中**或**年份接近」，而别名里混着「【原盘首发】怪奇物语 第四季」「2026年1月新番 …」这类带修饰的写法：它搜回一批不相干的结果、其中一个年份碰巧接近就会过门槛。假身份比没有身份糟得多——它带着 TMDb 链接和「已订阅」标记，看着比真的还可信。全等之后带修饰的别名自然对不上，等于自动跳过。
  2. **别名取自整组种子、按出现次数排序，只试前 `MAX_ALIAS_ATTEMPTS`(3) 个。** 干净的作品名每条种子都会写，修饰语各写各的；只看代表种子的话，它那条 description 恰好带修饰就整组落空。同一条种子里重复的别名只算一次。
  3. **别名尾部的季号先剥掉**（`SeasonSuffix#strip`，与刮削侧同一份）：TMDb 的条目名不带季号，「葬送的芙莉莲 第二季」带着它搜必然落空。
  4. **别名是兜底不是第二意见**：标题那条路识别出来了就不碰别名；与解析片名相同的别名也不再试（刚拿它问过）。
- **副标题（`subtitle`）是 description 的第一段原文**，取自 `DescriptionAliases#leadSegment`：段边界与 200 字上限同别名解析一份，过长的（没有 `|` 的剧情简介）不给。罗马音命名的种子，中文名常常只出现在这一段里，它是识别不出时用户自己辨认作品的依据。
- **「转为订阅」优先带识别出的规范名与类型**（`subscribeQuery`：有 `matchedTitle` 用它和 `mediaType`）：订阅页拿这个词去搜 TMDb，规范名一搜就是它，而罗马音 / 拼音命名的种子拿解析出的片名去搜多半落空。没识别出才退回解析出的片名（`parsedTitle`，去掉了分辨率与发布组），再不行用原标题；这时电影/剧集按「有没有季号或集号」判（`looksLikeMovie`，前后端同一判据）。落点是订阅页的 `?subscribe=片名&mediaType=TV|MOVIE`（`composables/useSubscribeDeepLink.ts`）：**用 watch 不用 onMounted**（订阅页开了 keep-alive，第二次跳过来 setup 不再跑），**处理完立刻 `router.replace` 抹掉这两个参数**（否则刷新一次就再弹一次弹窗）。没有订阅页菜单权限时提示而不是跳 404。
