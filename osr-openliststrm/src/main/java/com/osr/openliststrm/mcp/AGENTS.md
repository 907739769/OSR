# MCP 服务端

第五个控制面：传输、鉴权、权限档、后台作业。

## NOTES
- **MCP 服务端（`mcp/`）是 OSR 的第五个控制面**，与 Web、Telegram、企业微信、定时任务并列，本身不新增任何业务能力，只把已有能力包成工具给本地 AI 助理用。端点 `/mcp`，传输取 MCP Java SDK **核心包**自带的 Jakarta Servlet 实现（`HttpServletStreamableServerTransportProvider`），**刻意不引 Spring AI**——Spring 专用传输自 2.0 起已移交给 Spring AI（groupId 变成 `org.springframework.ai`），把它拖进来等于给本项目的 Spring Boot 4.0.6 装配再引一条独立的版本约束链。八条不要改坏的：
  1. **工具实现一律直接调用现有 Controller bean 的方法**（进程内方法调用，不走 HTTP），因为归属隔离（`denyIfInaccessible`）、`adminOnlyWrite`、敏感字段脱敏、进度计数填充全长在 Controller 上。绕到 Service 层自己拼一份判断，漂移的表现是「网页上看不到的订阅，助理能看到」——而这件事没有任何一层会报错。**环回 HTTP 调自己**也能避免漂移，但要多一跳、要自签 JWT、日志与 traceId 会打两遍。
  2. **身份靠 `McpCallContext` 显式绑定，绑定与恢复必须成对**（做成 `AutoCloseable` 就是为了让「忘了收尾」在语法上更难写出来）。工具处理函数**不在 servlet 线程上执行**（SDK 的同步服务端默认把它包成 `Mono.fromCallable(...).subscribeOn(boundedElastic)`，SSE 那条路径更是异步 servlet），所以 `CurrentUserContext` 与 `SecurityContextHolder` 都得自己填。漏绑定的表现不是报错而是「一条订阅都查不到」（当前用户为 null 时列表只放行无归属的公共订阅）；漏恢复的表现是偶发越权，而线程池必然复用线程。恢复用的是**保存-还原**而不是 `clearContext()`：那两个 ThreadLocal 未必属于我们。顺带一提，`CurrentUserContext` 这个 ThreadLocal 在此之前全项目没有任何过滤器填充它（`CurrentUserService` 的注释自己写着「直接读恒为 null」），MCP 是它的第一个真实写入方。
  3. **鉴权用独立的 `mcp_access_token` 表，不复用 JWT**。JWT 会过期，而且改密码会让此前签发的全部失效（`JwtTokenUtil#isInvalidatedByPasswordChange`）——助理是长期后台连接，用它等于设计上保证它天天掉线。明文只在签发响应里出现一次，库里存 SHA-256。**用 SHA-256 而不是 BCrypt** 不是偷懒：令牌是 32 字节高熵随机串而不是人选的口令，慢哈希要防的字典攻击在这里不存在；而每一次 `tools/call` 都要验一次，BCrypt 会给每次调用加几十毫秒，更要紧的是它只能把整张表拉出来逐行 `matches()`，而 SHA-256 能直接建唯一索引一次查中。
  4. **`/mcp` 刻意<b>没有</b>放进 permitAll 白名单**，照常受 `anyRequest().authenticated()` 约束：于是「令牌不对」由 Security 统一拦成 401，`McpAuthFilter` 只负责认证成功那条路径，不存在「某个分支忘了 return、请求带着空身份一路走下去」这类静默漏洞。它靠 `ModuleAuthenticationFilter` 这个标记接口被 `SecurityConfig` 插进 Security 链——**必须插进链里**，因为 STATELESS 下链最前面的 `SecurityContextHolderFilter` 会用空仓库覆盖 SecurityContextHolder，排在 Security 之前设置的认证信息会被原样擦掉。注入处的 `@Lazy` 也不能去掉（依赖链会经 `UserDetailsService` 绕回本配置类的 `passwordEncoder`），理由与 `jwtAuthenticationFilter` 完全相同；同时要用一个 `enabled=false` 的 `FilterRegistrationBean` 关掉 Spring Boot 对它的 servlet 自动注册，否则每个 `/mcp` 请求会执行两次过滤器（多一次令牌查库、多一次用户加载，而外层那次设置的 SecurityContext 随后会被覆盖掉，纯属白做）。
  5. **权限档（read/write/admin）是递进的，且与 OSR 自身的权限判定是<b>与</b>的关系**。给普通用户的令牌勾上 admin，它照样删不掉别人的订阅。分档依据是「做错了要花多大代价收回来」而不是「读还是写」：删订阅、重置集状态、拉黑发布组归 admin，建订阅、触发任务、重试归 write。
  6. **有一批操作压根没有对应工具，任何档都拿不到**：删网盘实际文件、删种（删种规则/转移规则的 run）、索引器/下载器/媒体服务器/参数设置的写与 `/test`（尤其 `/test`，它会把**已保存的**密钥填进请求、发往调用方指定的 url）、用户与角色。判据同上，而模型的误判在 MCP 上是**完全静默**的——客户端只会显示一句工具名。**更不要做 `call_api(path, method, body)` 这种万能工具**：它等于把两百来个端点连同上述一切一起交出去，而授权提示里只会写「调用 call_api」。`McpToolCatalogTest` 把工具清单逐字钉死，任何增删都必须同时改那份清单，也就必须被想一遍。
  7. **耗时超过十几秒的工具一律走 `McpJobService` 返回 jobId**，配 `get_job_status` 轮询。补搜一集的墙钟上限是「季搜索 30 秒 + 单集补发 180 秒」，而 MCP 客户端普遍 60 秒默认超时——同步等的结果是模型那边超时报错、服务端这边照样在跑，模型多半会**再调一次**，同一条订阅被并发补搜两遍。**刻意不用 SDK 的 progress notification**：那要求客户端实现 `progressToken`，各家参差。作业并发上限压到 2 是因为下游是索引器，多开只会在 `IndexerRateLimiter` 上排队并把等待推过 `max-wait-ms` 触发静默跳过（同 `AutoSearchService` 刻意串行）。
  8. **失败的 `Result` 必须转成 `isError=true`，不能原样序列化**。`{"code":500,...}` 与成功响应结构一模一样，模型多半会当作拿到了结果继续往下做；同时 OSR 这几个接口最有价值的信息就在 `message` 里（「未推送任何资源：98 个候选是非免费种」），所以拆包时要把它原样回给模型，别换成泛化文案。**后台作业里用的是另一种转法**（`McpResults#describe`）：「搜了一圈但一个都没推动」在接口语义里是 `Result.error`，可它不是「作业失败」——变成 FAILED 作业的话模型看到的是技术错误，会去重试，而重试改变不了任何事。
  **部署时最容易漏的一步是 nginx**：`/mcp` 必须单开一条 location 并 `proxy_buffering off` + 放大 `proxy_read_timeout`，不能靠现有的 `location /api/`（120 秒超时 + 默认开缓冲）兜住——端点也因此刻意不放在 `/api` 前缀下。症状很有迷惑性：握手正常、工具列表也拿得到，只有跑得久一点的调用会莫名断线。**读运行日志刻意没有做成工具**：实时日志页那套按行解析（`LogWebSocket.LineCodec`）与 `logback-spring.xml` 的 pattern 是一对隐性耦合，而它住在 osr-admin，`osr-openliststrm` 够不着；在 MCP 侧另写一份等于制造第二个会与 pattern 漂移的消费者。
- **MCP 工具的实现一律直接调用现有 Controller bean 的方法，不许绕到 Service 层自己拼一份判断**（`mcp/tool/`）。归属隔离、`adminOnlyWrite`、敏感字段脱敏、列表进度计数全长在 Controller 上，绕过它就是在 MCP 侧复制一份，而漂移的表现是「网页上看不到的订阅，助理能看到」——没有任何一层会报错。工具处理函数**不在 servlet 线程上执行**，所以身份要靠 `McpCallContext.bind()` 显式绑定并成对恢复，分页要靠 `PageContext`。完整的八条约束与「哪些操作压根没有对应工具」见本文件「MCP 服务端是 OSR 的第五个控制面」那条
